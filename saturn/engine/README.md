# Saturn engine patches

This package makes the code changes the translation needs to display properly.
`build.py` reads the original binaries straight from the verified source disc,
applies the selected patches in memory, and writes the results to
`generated/<disc>/` (ignored by Git). The normal Saturn build then copies those
outputs into the extracted disc directory.

Layout:

- `surfaces/`: one module per screen or feature ("surface").
- `core/`: binary patching, patch-config loaders, and the SH-2 assembler.
- `shared/`: small rendering helpers used by more than one surface.
- `asm/` and `config/`: assembly sources and patch configs (both readable).
- `build.py`: runs the surfaces, writes outputs, and provides the CLI.

## Surfaces

There are 24 surface commands. Some produce a final file; others produce an
intermediate file that a later surface builds on:

| Family | Surface commands |
| --- | --- |
| Akuma Zensho | `compendium.text` |
| Profile and standalone overlays | `profile_entry.ui`, `map_2d.ui`, `horoscope.ui`, `credits.ui`, `diagnostics.ui`, `portrait_scene.ui` |
| EVENT and COMP composition | `event.dialogue`, `fusion.menu`, `event.name_inserts`, `comp.menu`, `equipment.ui`, `facilities.status_ui`, `fmv.subtitles` |
| Battle | `battle.negotiation`, `battle.ui` |
| Standalone game interfaces | `status.ui`, `options.ui`, `level_up.ui`, `map_3d.analyze` |
| MAZE family | `dungeon.locations`, `field.messages`, `maze.party_panel` |
| Save system | `save_load.ui` |

The default Saturn profile runs these in dependency order, installs each final
file once, applies the image replacements afterwards, and then rebuilds both
discs. Intermediate files and their manifests stay around for individual
checks, but only the last stage for a given file is ever installed.

## Assembly

Code changes are written as SH-2 assembly under `asm/`. The small assembler in
`core/sh2.py` supports only the instructions and directives those sources use,
and rejects unknown syntax, unresolved symbols, bad branches, and unsafe delay
slots. Patch configs (version 2) list the original bytes expected at each site,
the size of each code cave, source paths, pointer targets, and single-instruction
edits. They don't contain pre-assembled machine code.

Python links the assembly against data generated from the text and font assets
and applies the patches. Generated bytes are build output and aren't committed.
Hashes from the earlier reference build are kept only as regression tests, so
you can read and change the actual code instead of decoding hex out of JSON.

Every ported surface works this way. Common routines sit at the top of `asm/`;
a surface only gets its own copy when its calling convention or rendering
actually differs. A test fails on version-1 configs or on any `replacement`
machine-code blob.

## Akuma Zensho text

> **Broken.** This surface builds and passes its checks, but the translated
> compendium does not work correctly in game. The description below is how it
> is meant to work, not a sign that it does.

`compendium.text` builds all the known text on the bonus disc: 292 profile
tails, plus the demon, ability, race-label, race-description, fusion-help, and
twelve status-label records in `A_DIC.BIN`. Row sizes:

- profiles: one 144-pixel origin row, four 224-pixel summary rows, and twelve
  224-pixel detail rows;
- names and abilities: 128-pixel rows;
- race labels: 48-pixel rows;
- race descriptions: a 224-pixel heading plus four 224-pixel prose rows;
- fusion help: two 320-pixel rows.

Generated rows use a reversible tagged encoding and a dictionary derived from
the text assets. An SH-2 wrapper temporarily draws decoded FONT8 glyphs into the
compendium's existing FONT16 work area, calls the original drawer, and then
restores the original cells. A separate single-glyph adapter pre-draws the six
two-letter base-stat labels, while the shared row adapter handles the six
derived-stat labels. Both keep their scratch data inside the zero-filled area of
the executable rather than the live `0x00288000` render buffer. The code uses
2,960 bytes of the 30,722-byte zero area in `A_DIC.BIN`. No compendium font cell
or font file is reused. Vengeful Spirit and Fiend are translated; two raw
placeholder race rows are left identical to retail because nobody has worked
out what they are.

The builder reads all 293 targets from the verified source disc, writes them
to `engine/generated/compendium/`, and installs the full files before the
image pass. Check mode compares `A_DIC.BIN` exactly, and compares the 292 text
tails that sit beneath the later profile images. There's no earlier reference
build to compare against for this disc, so the checks instead pin every source
hash and patch span and decode every generated record back to its text.

Run:

```powershell
python saturn/engine/build.py compendium.text
python saturn/engine/build.py compendium.text --check
python saturn/engine/build.py compendium.text --install
```

## Profile Entry

`profile_entry.ui` builds the `NAME.BIN` name-entry screen from the verified
retail file, the Profile Entry text assets, and the generated FONT16, FONT8, and
KANJI atlases. It never reads the extracted disc directory. The generated font
binaries and metrics are inputs to the code itself: the controller builds its
saved-byte conversion tables, character widths, and input-grid codes from them.

The 6,840-byte region freed from the original code is treated as one space
rather than a fixed code/data split. Tables built from the assets fill it from
the start, the controller code is aligned and assembled straight after, and
every hook is linked to the resulting labels. The build only fails if the total
runs past the end of the region. The default build uses 5,348 bytes, leaving
1,492 bytes free.

Prompts, choices, tabs, occupations, grid rows, and defaults come from
`assets/text/ui/profile_entry.json`. The NAME_FW_FULL name order and separator
come from `assets/text/player_profile.json#full_name_storage`.

- The eight-cell name row centers the existing 12px Ark FONT16 glyphs at
  runtime.
- Grid cells use the generated 16px Ark KANJI glyphs and their measured ink
  bounds; the controller centers each one in its cell when drawing.
- The confirmation prompt and choices are proportional FONT16 text instead of
  the original fixed-width template, with YES and NO centered where the
  original choices were.

The output hash is
`9143d8961f1193aa23a8033f70c829214fa7a40e149e6467b335f23e7ad61f41`.
The default build installs `NAME.BIN` right after the generated fonts.

Run:

```powershell
python saturn/font/repack.py all
python saturn/engine/build.py profile_entry.ui
python saturn/engine/build.py profile_entry.ui --check
python saturn/engine/build.py profile_entry.ui --install
```

## Two-dimensional map

`map_2d.ui` builds the `MAP2D.BIN` city map from the verified retail file, the
generated FONT16 atlas and metrics, and the shared text. The starting city and
ward reuse the Profile Entry defaults, the five destination rows reuse the
location list, and the conversation prompt and choices reuse the field
messages. `Mt. Kasagi` is the only map-specific short form. The builder never
reads the extracted disc directory.

Display limits are the 96-pixel world-city box, the 64-pixel region strip, and
the 128-pixel area box. To match the earlier reference build exactly, the code
currently fits each dynamic name in 64 pixels and hides the city part of the
name on the area screen. It also leaves off the `市全図` suffixes on the world
screen; that template is still editable rather than hard-coded. The standalone
cloud row stays in the text package and isn't used here, because nothing has
been found that displays it.

All code changes come from the two sources under `asm/map_2d_ui/` and the 24
recipes in `config/map_2d_ui.json`. City and ward names are read through the
player-name layout in `shared/player_names.py`; the build doesn't read the
generated `NAME.BIN`. The three code caves use 2,166 of 2,756 available bytes,
including an eight-byte FONT16 scratch area. The output hash is
`dce250711d7a596bb6c675c76c8cc30542181f00570c5bd4a92d3b7eca6b1123`.
The default build writes its manifest after Profile Entry and copies
`MAP2D.BIN` into place before the later image overlays.

## Horoscope vision

`horoscope.ui` rebuilds the eight story messages in `HOSI.BIN` from
`assets/text/ui/horoscope.json` and the generated FONT16 metrics. The original
renderer is left alone. Text only wraps at spaces, each message is limited to
three 20-cell rows and 64 reveal words, and the messages are written into the
1,024-byte zero area at `0x06020400`.

The eight message pointers are linked to wherever the messages end up, so
changing a message's length moves the ones after it instead of breaking.
One instruction edit scales the original reveal counter so text still appears
progressively. The default messages use 668 bytes, and the output matches the
earlier reference `HOSI.BIN` (SHA-256
`b51a5611e1095387c92baec2a5f8a8965eb47794cab0b774add3eb310f04b041`).
The normal build installs it once, after MAP2D and before the EVENT banks.

## FMV subtitles

`fmv.subtitles` is the last EVENT stage. It reads the nine START2 news-report
cues from `assets/text/fmv/subtitles.json`, converts their centisecond timings
into frame ranges on the 12 fps, 401-frame movie, and centers each line using
the generated FONT16 Ark 12px widths.

It doesn't touch the movie file. It verifies the hash of the retail
`BGDATA/START2.CPK` and patches only `EVENT.BIN`. The SH-2 code detects START2
on the blocking, queued, and direct asynchronous movie start paths and wraps
the original frame presenters. Each wrapper lets the original presenter copy
the decoded frame first, then draws the subtitle into that presenter's VDP
destination. The Saturn B-bus orders those writes after the active SCU DMA, so
Cinepak's reference frame is never modified, and the next frame clears an
expired subtitle without any extra erasing. Streaming playback draws RGB555
640-byte rows; blocking playback draws 32-bit RGB 2,048-byte VDP rows. Timing
only advances when a decoded frame is ready.

The subtitle data includes the 32 FONT16 glyphs it needs and uses 1,894 of
1,952 available data bytes; the code uses 564 of 704 bytes. It doesn't rely on
FONT16 already being in work RAM. The original 9,134,032-byte CPK is left
unchanged.

Run:

```powershell
python saturn/engine/build.py fmv.subtitles
python saturn/engine/build.py fmv.subtitles --check
```

## Event dialogue

`config/event_dialogue.json` ties the `event.dialogue` surface to two groups of
`EVENT.BIN` patches:

- `event_vwf`: the FONT16 variable-width renderer, menu paths, and the
  two-glyphs-at-a-time typewriter speed used by the earlier Saturn translation.
- `event_packed_fetch`: decodes the compressed EVENT text produced by
  `text/repack.py` using the configured dictionary table.

The code caves are rebuilt from the sources under `asm/shared/event_window/`
plus the shared FONT16 renderers. The build fails on changed inputs, overlapping
patches, wrong metrics or dictionaries, out-of-date text outputs, or output
that drifts from the earlier reference build.

The same EVENT code also draws the normal dialogue and direct FONT16 menu
records in `SHOPSMP.EVE`; shop dialogue doesn't have its own text hook.

## Portrait-scene event window

`portrait_scene.ui` builds `MSGR.COF`, the portrait-scene dialogue window, from
the verified retail file. It uses the same `event.dialogue` text and the same
three-row, 300-pixel wrapping as the general EVENT window; there's no separate
portrait dialogue bank. Before assembling, the builder checks the EVENT build
manifest, all four generated EVE banks, the shared compression dictionary, and
the generated FONT16 and FONT12 layouts. The generated FONT8 font and metrics
also fix the name-pool byte mapping. `SHOPSMP.EVE`, built later, is another
bank read by the same code, not an input to this build.

All 37 patch sites are applied together because they depend on each other:

- `msgr.dialogue_vwf`: 14 sites for proportional dialogue, menus, decompression,
  and the typewriter effect.
- `msgr.term_inserts`: four sites for character, demon, and race substitution,
  plus their generated pools.
- `msgr.player_name_adapters`: 15 adapters for first name, last name, codename,
  city, ward, and the raw choice menu.
- `msgr.fixed_text_compatibility`: keeps the direct `UMA` race copy.
- `msgr.debug_messages`: rebuilds the three on-screen ASCII debug messages from
  `assets/text/system/debug.json`. These still use MSGR's own fixed-width glyph
  tiles rather than FONT8 or FONT16.

The code is assembled from the shared event-window and player-name sources plus
the common FONT16 subpixel blitter. Character, demon, race, and debug data come
from the assets, bindings, and corpora. Space used:

- dialogue: 2,113 of 19,456 bytes;
- full-term pool: 4,480 of 5,376 bytes;
- raw-name menu: 86 of 96 bytes.

The build manifest records each area's address and size, plus the total of
6,679 of 24,928 reserved bytes.

The player-name adapters only rely on the WRAM layout in
`shared/player_names.py`; they don't import Profile Entry or read any generated
or installed `NAME.BIN`. The builder never reads the extracted disc directory.

The default output matches the earlier reference build byte for byte (SHA-256
`3cbbf6ec70887cdb49a46c006767550438da684a30b5a754d6ce7c811d337814`).
The normal build writes `MSGR.COF` and its manifest, then copies it into place
right after the four general EVENT banks. No image replacement touches MSGR.

## Shared battle UI

## COMP core

shared FONT8 party-panel and item/magic-grid renderers, the item-name pointer
reader, and the full-width FONT16 help renderer. It writes an intermediate

The code rebuilds its FONT8 width tables and all the long character/demon name
data from the current font metrics, `characters.json`, `demons.json`, and the
generated `DVLNAME.DAT`. Names that fit the original record are stored there
directly; longer names go into low/high compact pools, which editors never
have to deal with. The party panel, item and magic grids, help reader, cursor
movement, and shared FONT8/FONT16 drawers are rebuilt from assembly. Their data
addresses and caller pointers are re-linked whenever the generated pools move.

`NORMHELP.DAT`, `DVLNAME.DAT`, `ITEMNAME.DAT`, and `MAGNAME.DAT` are still
ordinary text-build outputs. The NORMCOM result matches the earlier reference
patches byte for byte, and the build fails on changed source bytes, out-of-date
text or metrics, names that are too long, unsupported compact characters, or
cave overflow.

earlier reference build exactly, and the visible serif heading is an image
anyway. Controller button icons and the SEGA logo are also images, not text.

`config/options_ui.json` has 57 recipes: four assembly regions, 24 generated
data regions, 17 instruction edits, and 12 linked pointers. The five sources
under `asm/options_ui/` handle the variable-width labels and actions, redrawing
the active row, and a local combined-glyph renderer. Width tables, popup rows,
the action atlas, labels, and footer records are regenerated from the current
assets and FONT16 build. The short combined-glyph cells are generated from the
full phrases, so strings like `Recovery` and `START: Assign` only exist in one
place.

The output matches the earlier reference build byte for byte at
`6d25bab3b2137a3f5fea49d69bcf374a918f68fe5d26f170139f6a76c5fce010`.
The build also checks that the retail magic sort order is unchanged, and keeps
the global input-end glyph reserved when allocating combined-glyph cells.

Run:

```powershell
python saturn/engine/build.py options.ui
python saturn/engine/build.py options.ui --check
python saturn/build.py default
```

## Level Up

`level_up.ui` builds `LEVEL_UP.BIN`, which has two parts: the normal stat and
confirmation panel, and Rei's separate two-row Learned Magic window. The default
output matches the earlier reference build at
`466c552e95bb5c7bd808f550e8f0832077715f20fd5427dedf412793fe5d1ed1`.

`config/level_up_ui.json` has 21 recipes: three assembly regions, three linked
pointers, and 15 generated-data regions. Six sources under `asm/level_up_ui/`
handle the FONT16 name and ability drawing and two fallback number formats. The
code takes up 1,279 of the 1,280 zero bytes at `0x06022000`. The last byte is
kept as a hard limit, so there's effectively no room to grow.

Every visible word and symbol comes from the text assets. The five fixed
character selectors are Rei, Kyouji, Taro, Jiro, and Saburo; the player's
codename is a separate 128-pixel dynamic field. Learned abilities use the 255
Saturn MAGNAME bindings rather than joining the shared asset lists together.
The LV/HP/MP/EXP/NEXT templates carry their own punctuation. The max-level
`-------` and no-MP `---/---` forms are editable even though retail builds them
in code; the alternate assembly for them is only used when they're changed, so
the default text keeps the retail bytes.

`level_up_ui_build.json` records the original file, fonts, generated MAGNAME
manifest, the assets/bindings/corpora used, the assembly sources, the patch
list, and the final hash.

Run:

```powershell
python saturn/engine/build.py level_up.ui
python saturn/engine/build.py level_up.ui --check
python saturn/build.py default
```

## 3D Map Analyze

`map_3d.analyze` builds `DA_3D.BIN` in one go for both the sortable Analyze grid
and the selected-demon detail panel. The output matches the earlier reference
build at
`3d84b647018108d6a2f1f74a068336d6166766b1a3d25d826f7eb05c66f2efe7`.

`config/analyze_ui.json` has 37 recipes:

- 14 reproduce the earlier build's code, hooks, English name sorting, and
  status graphics;
- 17 generated records drive every retail heading, number prefix, alignment
  axis, and skill-cost unit from the text assets;
- 6 conditional recipes split retail's shared Law/Light `L` only when the two
  are edited to differ, so the default output stays exact.

Eleven sources under `asm/analyze_ui/` provide the FONT8 and FONT16 drawers,
name decoder, affinity and skill dispatchers, grid/detail dispatcher, English
sort comparison, and the conditional axis split. The main code uses 3,510 of
its 3,522-byte region; the separate table code uses 256 of 258 bytes. The 52
bytes in use between those regions are left alone rather than treated as free
space.

The builder reuses the shared demon, race, affinity, status, alignment, magic,
and skill assets. The 43 katakana race names in the grid are variants of the
same race entries, not separate translations. Fixed Latin labels use the
original Japanese FONT8 English alphabet through the `stock_latin` handler. The
affinity dictionary is generated from the full descriptions, so the compressed
phrases aren't a second copy of the text to maintain.

## Dungeon locations

`dungeon.locations` rebuilds the location display in `MAZE.BIN`,
`AUTOMAPC.BIN`, 17 landing files, and 98 floor files. Its 117 original files
are read from the verified game disc and patched by 302 recipes. The MAZE and
AUTOMAP renderers come from the sources under `asm/dungeon_locations/`;
location names, floor templates, AUTOMAP aliases, and marker labels come from
the shared text assets through their bindings.

The builder writes every AUTOMAP and MAZEDATA result to its final path, but
writes MAZE to `generated/game/dungeon_locations/MAZE.BIN` as an intermediate,
so two stages never both claim the final MAZE file.
`dungeon_locations_build.json` records all 117 source hashes, output hashes,
assembly inputs, and the 302 patches.

The location tables and every ELV/KAI copy match the earlier reference build.
MAZE also redirects the elevator-only drawer pointer at `0x0603CFC4` to a
variable-width adapter. Its lower symbol, floor symbol, and three-part
placeholder order come from `assets/text/field/elevator.json`, separately from
the 3D-map floor wording. AUTOMAP leaves the retail `YES`/`NO` bytes in place
(they're no longer read); the visible text comes from the shared choice fields
through the new renderer.

## Field messages

`field.messages` adds the fixed field-message window on top of that MAZE
intermediate and writes the next stage, `generated/game/MAZE.BIN`. Messages,
confirmation choices, currency symbols, and item substitutions all come from
the text assets; the assembly only handles display, substitution, and layout.
Its manifest records both the incoming MAZE hash and the dungeon-location
manifest, so neither stage can change without the other noticing. Both
`dungeon.locations` and `field.messages` can still be built and checked on
their own.

The six unchanged fixed messages match the earlier reference bytes. The final
MAZE hash is different on purpose
(`f89e4df13f4ea92524338b106493ec504f63cc514f51682292c3563e57c34e75`): the old
build accidentally sent the item-obtained message through `Found`, used broken
item-full wording, and dropped the final punctuation from currency messages.
The new hooks use the full templates from the text assets instead.

## MAZE party panel

`maze.party_panel` is the last MAZE stage in the default build. It adds the
compact party-list name renderer on top of the `field.messages` output and
keeps the other 116 final AUTOMAP and MAZEDATA outputs. It shares the compact
name compiler with `comp.menu`; all 319 demon names and six character names
still come from the text assets and the freshly generated `DVLNAME.DAT`.

Five recipes cover two separate zero caves and the three drawer pointers. The
sources `font8_pixel_blitter.s`, `font8_fixed_name.s`, and
`comp_menu/party_panel.s` assemble to 2,038 bytes within 3,072 bytes of space.
The renderer area ends exactly where the field-message cave starts, and the
compact-name area starts at the field-message cave's end, so the three MAZE
patches can't overlap. The default final SHA-256 is
`c45b897557852679a855b8c4e01c627fd2531d8b5be07072bb49de5a0ff2e5e1`.

## Save and Load

`save_load.ui` builds `SAVE.BIN` and `LOAD.BIN` together. The two programs share
the player-name code, the proportional location renderer, the dungeon location
records, and the system-message layout, so one builder writes both files and a
single `save_load_ui_build.json` manifest. It reads the retail SAVE, LOAD, and
MAZE files straight from the verified game disc, never from the extracted disc
directory.

All visible text comes from the Save/Load, location, and floor-format assets
through their bindings. The slot line uses its own order from
`save_load.json#slot_name`, while LOAD rebuilds the shared NAME_FW_FULL row from
`player_profile.json#full_name_storage`. Both placeholder orders and one mapped
FONT16 separator glyph are supported, so Profile Entry and LOAD always agree
after a save and load. The engine code only handles drawing, rebuilding names,
and layout. The engine-only outputs are
`3f97ac9b7f40af32c1314a00311a15079c1a402bc0b3822d2b1d90fbab2c5b57`
for SAVE and
`a9a58b2fa5c4c0e96298c6ec2fcdf84999e695d084556f53c33db3c2afad959f`
for LOAD.

Every translated row is checked against both its pixel width and the number of
glyphs it can hold; both limits are listed together in the surface catalogue.

The four Internal/Cartridge selector images belong to the image package. The
default profile installs both engine outputs right before `repack_visuals`,
which overlays four RGB555 image spans in each file. Check mode compares every
non-image byte against the engine outputs, then the image check validates those
eight spans. The final combined hashes, matching the earlier reference build,
are
`ccbff9a2dedd4b65c073dd1e59b343602c52f80f2ad431309b23dba86e1c0d31`
for SAVE and
`13ea4b16836906ae75e5d08d622bd10f513c31bdbf42d7a8930abd99475eb82a`
for LOAD.

Run:

```powershell
python saturn/engine/build.py save_load.ui
python saturn/engine/build.py save_load.ui --check
python saturn/build.py default
python saturn/build.py default --check
```

## What's left

The surfaces above cover every Saturn code patch that's currently known to be
needed. What isn't done:

- The main battle-selector lettering is part of a graphic or font, not a text
  record, so it's left as is.
- The MAP2D cloud row and two raw compendium race placeholders are left as
  retail, because nobody has found what displays them or what they are.
- Words inside images stay with the image package until there's a way to
  generate those graphics from text.
- PSP needs its own package (see `psp/`), not more Saturn recipes.

Unknown pixel limits in `text/config/surfaces.json` still need measuring; they
don't mean anything is missing from the engine. The normal build and each
surface's `--check` are what tell you whether outputs are up to date.
